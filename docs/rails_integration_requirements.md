# Доработки гема под встраивание в Rails-приложение и админку

Требования к гему `gar` со стороны первого потребителя — портала «Первоисточник» v4.
Документ описывает, **что** нужно приложению и **почему**; как это сделать в геме,
решает разработчик гема. Ссылки на код даны по версии 1.0.0 (`75bac60`).

## 1. Потребитель и сценарии

**Приложение:** Rails 8.1, Ruby 3.4, PostgreSQL 18. Веб-сервер — Puma с потоками
(в проде, возможно, и с воркерами-процессами). Фоновые задачи — Solid Queue: супервизор
форкает процессы воркеров. Админка — ActiveAdmin, поля форм с автодополнением — Tom Select,
он ходит в JSON-эндпоинт. Деплой — Docker в Dokploy.

**Регионы портала:** Киров (субъект 43, Кировская область) и Сыктывкар (субъект 11,
Республика Коми). Адрес вне этих субъектов — редкость: например, головной офис
всероссийской фирмы. Его можно вводить вручную, без ГАР.

**Сценарии, ради которых подключается гем:**

| # | Сценарий | Где | Частота |
|---|---|---|---|
| С1 | Автодополнение адреса в форме филиала организации: ввёл «Ленина 10» — выбрал дом — форма получила GUID, разобранные поля, индекс | запрос админки, поток Puma | десятки в день, ответ нужен быстро |
| С2 | Сопоставление адресов при переносе справочника из старой версии сайта: 5 881 адрес, у каждого GUID ФИАС **улицы** (1 056 улиц) и номер дома, корпус, строение, дробь — текстом | фоновая задача, разово и при повторных прогонах | пачкой, тысячи за прогон |
| С3 | Регион портала по адресу: адреса фильтруются по региону | при сохранении адреса | на каждую запись |
| С4 | Загрузка и обновление базы ГАР | фоновая задача или rake на сервере | раз в месяц или реже |
| С5 | Спеки приложения без полной базы ГАР | CI и локальный прогон | на каждый прогон |

Требование портала (`ai_docs/v4/06_требования_к_интеграциям.md` §1.5): данные ГАР —
только для чтения; при недоступности ГАР адрес вводится вручную; после выбора адреса
приложение само геокодирует его через Яндекс. Геокодирование, модель адреса и интерфейс
остаются в приложении, гем ими не занимается.

## 2. Что есть сейчас (1.0.0)

- **Скачивание.** Полный архив (`Gar::Downloader`); дельты — «в разработке».
- **Импорт.** Импорт в версионированную схему `gar_v<дата>`, переключение переименованием
  схем с резервной копией (`Gar::Importer#switch_to_imported_schema`).
- **Фильтры импорта.** По актуальности, активности и уровню объекта
  (`config.entity_options`, парсеры `entities/*/parser.rb`).
- **Поиск.** `Gar::Search`: полнотекстовый по объектам и домам, каскадный
  (`find_address_objects`, `find_houses`), по GUID. Ответ — строки `MiniSql`.
- **Соединение.** Своё, через `pg` и `mini_sql`, мимо пула Active Record.
- **Логгер.** По умолчанию — `Rails.logger`, если он есть.

## 3. Требования

Приоритет: **P1** — без этого встраивать нельзя; **P2** — нужно к первому рабочему
сценарию; **P3** — удобство и эксплуатация.

### P1. Безопасная работа внутри Rails-процесса

**Т1. Не подключаться по умолчанию к базе приложения.**
- **Проблема.** `Configuration#initialize` берёт `ENV.fetch("DATABASE_URL", …)`
  (`lib/gar/configuration.rb:13`). В Rails-приложении `DATABASE_URL` — это база самого
  приложения. Забытая настройка — и гем молча ищет таблицы ГАР в чужой базе, а импорт
  создаёт схемы там же.
- **Требование.** Своя переменная (`GAR_DATABASE_URL`) или только явная настройка. Без
  настройки — понятная ошибка при первом обращении, а не тихое подключение.
- **Готово, когда:** при пустой настройке `Gar::Search.new.search_houses("…")` бросает
  ошибку конфигурации с подсказкой.

**Т2. Потокобезопасный доступ к базе.**
- **Проблема.** `Gar::Database.connection` — одно `PG::Connection` на процесс
  (`lib/gar/database.rb:58-63`). Мьютекс защищает только создание соединения, но
  не запросы. `Gar::Search.new` без аргумента берёт именно его (`lib/gar/search.rb:14`).
  Два потока Puma с одновременным автодополнением будут слать запросы в одно соединение,
  а `PG::Connection` для этого не предназначен.
- **Требование.** Пул соединений с настраиваемым размером и таймаутом ожидания
  (например, гем `connection_pool`) и блок `Gar.with_connection { |conn| … }`. `Search`
  берёт соединение из пула на время вызова, а не держит его.
- **Готово, когда:** спека гоняет N потоков с параллельным поиском без ошибок; размер
  пула задаётся настройкой (`config.pool_size`, по умолчанию — 5).

**Т3. Корректная работа после `fork`.**
- **Проблема.** Супервизор Solid Queue, Puma в кластерном режиме и
  `parallel_import_strategy :processes` форкают процесс. Соединение, открытое до форка,
  наследуется детьми: два процесса пишут в один сокет.
- **Требование.** После форка соединения родителя не используются: пул сбрасывается
  (хук `Process._fork` или проверка `Process.pid` при выдаче соединения).
- **Документировать:** на macOS `libpq` с Kerberos падает segfault'ом в форкнутом
  процессе — приложение лечит это `gssencmode=disable` в строке подключения. Строке
  подключения гема нужно то же; README должен это упомянуть.
- **Готово, когда:** спека открывает соединение, форкается, и ребёнок делает запрос
  без ошибки и без порчи соединения родителя.

**Т4. Таймауты.**
- **Проблема.** Автодополнение не должно держать поток Puma дольше секунды, а
  недоступный сервер ГАР не должен вешать форму.
- **Требование.** Настраиваемые `connect_timeout` и `statement_timeout` для поиска
  (отдельно от импорта, где запросы идут часами).
- **Готово, когда:** при недоступной базе `Gar.available?` (см. Т14) отвечает `false`
  за время `connect_timeout`, а поиск бросает собственную ошибку гема
  (`Gar::UnavailableError`). Приложение ловит её и переключает форму на ручной ввод.

### P1. Объём базы

**Т5. Импорт только нужных субъектов.**
- **Проблема.** Полный архив — 52,9 ГБ (`gar_xml_v20260116.zip`), база после импорта —
  30–50 ГБ, импорт — 4–8 часов. Порталу нужны два субъекта из 89. Архив разложен
  по папкам субъектов (`43/…`, `11/…`), справочники типов лежат в корне. Сейчас XML
  выбираются только по имени таблицы (`entry.name.include?(table_key)`,
  `lib/gar/importer.rb:351-352`). Фильтра по субъекту в 1.0.0 нет; если он уже есть
  в текущей версии — описать его в README.
- **Требование.** `config.region_codes = %w[43 11]`: из архива распаковываются
  и импортируются только папки этих субъектов плюс корневые справочники. Пустой
  список — все субъекты.
- **Готово, когда:** импорт двух субъектов не распаковывает остальные папки. В README —
  замер времени и размера базы для такого импорта.

### P2. Поиск для формы (С1, С3)

**Т6. Поиск в границах субъекта или населённого пункта.**
- **Проблема.** Ни один метод `Gar::Search` не принимает границу поиска. «Ленина 10»
  находит дома по всей стране, а портал — региональный.
- **Требование.** Необязательные параметры `region_codes:` (по
  `adm_hierarchy.region_code`, колонка уже есть) и `within:` (GUID города или района)
  у всех методов поиска.
- **Готово, когда:** `search_houses("Ленина 10", region_codes: ["43"])` не возвращает
  дома других субъектов.

**Т7. Одна строка ввода — улица и дом в одной выдаче.**
- **Проблема.** Сейчас это два вызова: `search_address_objects`, затем `find_houses`
  по улице. Форма с одним полем ввода («Киров, Ленина 10б») должна сама решать, что
  искать.
- **Требование.** Метод автодополнения: принимает строку и границу (Т6), возвращает
  смешанный список улиц и домов с ранжированием (точное совпадение номера дома — выше).
  Каждый элемент — сериализуемый `Hash` или `Data`, без объектов `MiniSql`: приложение
  отдаёт его в JSON как есть.
- **Готово, когда:** на базе двух субъектов p95 ответа ниже 100 мс. Замер — в README.

**Т8. Полные сведения об адресе по GUID.**
- **Проблема.** В таблице `houses` нет дополнительных номеров: корпуса, строения и их
  типов (`ADDNUM1`, `ADDTYPE1`, `ADDNUM2`, `ADDTYPE2` из `AS_HOUSES`;
  `lib/gar/entities/houses/table.rb:9-24`). Без них «д. 10 корп. 2» не отличить
  от «д. 10», и адресная строка неполна. Индекс и коды ОКАТО и ОКТМО лежат в `params`,
  но поиск их не возвращает.
- **Требование.**
  - Импортировать дополнительные номера домов.
  - Метод `Gar.address(guid)` возвращает разобранный адрес: GUID и уровень объекта, код
    субъекта, субъект, город или населённый пункт, улица, дом, корпус, строение, индекс,
    ОКТМО, цепочка GUID родителей и строка адреса. Строка собирается по правилам
    ФНС (`docs/Правила_формирования_адресной_строки.docx`).
- **Готово, когда:** для дома с корпусом и строением метод отдаёт все поля, а строка
  совпадает с примером из правил ФНС.

**Т9. Код субъекта в каждом результате.**
- **Проблема.** Портал выводит свой регион из субъекта адреса (сценарий С3).
- **Требование.** `region_code` в каждом элементе выдачи поиска и в ответе `Gar.address`.

### P2. Сопоставление старых адресов (С2)

**Т10. Пакетный поиск по GUID.**
- **Проблема.** `find_address_object_by_guid` — один запрос на GUID. Для 1 056 улиц это
  терпимо, но для повторных прогонов нужен пакет.
- **Требование.** `find_address_objects_by_guids(guids)` — один запрос, ответ —
  `Hash` guid → объект.
- **Проверить и описать в README:** совпадает ли `OBJECTGUID` ГАР с `AOGUID` ФИАС для
  улиц. На этом держится весь перенос; проверить на выборке GUID из субъекта 43.

**Т11. Сопоставление дома по улице и номеру.**
- **Проблема.** В старых данных дом записан текстом: номер, литера, корпус, строение,
  дробь (`10`, `10а`, `10/2`, `корп. 2`).
- **Требование.** `match_house(street_guid:, number:, letter:, building:, structure:)`
  нормализует запись и возвращает лучший кандидат с признаком точности (`:exact`,
  `:fuzzy`, `:none`) и список альтернатив.
- **Готово, когда:** спека на таблице примеров из старых адресов проходит, несовпавшие
  получают `:none`, а не случайный дом.

### P2. Загрузка и обновление из приложения (С4)

**Т12. Программный API импорта для фоновой задачи.**
- **Проблема.** Приложение ведёт долгие прогоны своей моделью `BackgroundRun`: прогресс
  на пульте в админке, отчёт, защита от двойного запуска. Гему нужно отдавать прогресс
  наружу, а не только в лог.
- **Требование.**
  - Шаги `download`, `import`, `build_paths`, `switch` вызываются по отдельности и
    принимают `on_progress: ->(done, total, stage) {}`.
  - Ошибка — исключение гема с понятной причиной; ни `exit`, ни `puts`.
  - Повторный вызов шага безопасен: незавершённая схема удаляется или переиспользуется.
- **Готово, когда:** пример в `examples/` показывает импорт двух субъектов из ActiveJob
  с прогрессом.

**Т13. Версия загруженной базы и обновления.**
- **Проблема.** Приложение должно знать, какая версия ГАР загружена, а дельты пока
  «в разработке».
- **Требование.**
  - Служебная таблица в схеме (`meta`: `version_id`, дата выгрузки, `region_codes`,
    время импорта) и `Gar.current_version`.
  - Применение дельт — по возможности. Если дельт не будет, README прямо говорит:
    обновление — это полный повторный импорт нужных субъектов.
  - Политика резервных схем: сколько хранить и чем удалять старые
    (`backup_current_schema`, `lib/gar/importer.rb:67`). Каждая копия — гигабайты
    на диске сервера.

**Т14. Проверка доступности.**
- **Требование.** `Gar.available?` — быстрая проверка соединения и наличия текущей
  схемы с построенными путями (`full_adm_path`).
- **Зачем.** По ней приложение решает, показывать автодополнение или ручной ввод.
  Ту же проверку можно повесить в health-эндпоинт.

### P3. Удобство встраивания

**Т15. Railtie.**
- Rake-задачи `gar:download`, `gar:import[region_codes]`, `gar:switch`, `gar:status`.
- Генератор инициализатора с закомментированными настройками.
- Логгер приложения уже подхватывается — оставить так.

**Т16. Поддержка тестов приложения.**
- **Проблема.** Спекам приложения нужен маленький набор ГАР (несколько улиц и домов
  Кирова с корпусами), а не полная база.
- **Требование.** В геме уже лежат `spec/fixtures/schema.sql` и `data.sql`. Выдать их
  наружу как `Gar::TestSupport.load_fixtures(conn, schema:)`, а набор пополнить адресами
  субъекта 43: дом с корпусом, со строением, с дробью, с литерой.

**Т17. Инструментирование.**
- Если определён `ActiveSupport::Notifications`, гем публикует события поиска
  (`search.gar` с длительностью и числом результатов). Приложение видит их в логах
  и в APM.

**Т18. Пользователь базы только на чтение.**
- **Документировать:** поиск работает под пользователем с `SELECT` на текущую схему,
  импорт — под отдельным пользователем с правом создавать схемы. Приложению
  в запросе читателя не нужны права на запись.

**Т19. README без противоречий.**
- Сейчас в README «минимум 150 ГБ свободного места» и «размер базы 30–50 ГБ».
- Нужна таблица: архив, распаковка, база — для полного импорта и для двух субъектов.

## 4. Чего гем делать не должен

- Модель адреса, связь с организациями и филиалами — в приложении.
- Геокодирование (Яндекс Geocoder) и координаты — в приложении.
- JSON-эндпоинт, контроллер, Stimulus-контроллер поля — в приложении. Гем отдаёт
  данные, готовые к сериализации (Т7).
- Привязка к Active Record — не нужна. Своё соединение — правильное решение: база ГАР
  отдельная и большая, ей не место в пуле приложения.

## 5. Открытые вопросы

1. **Где база ГАР на проде:** отдельный сервер PostgreSQL или отдельная база рядом
   с базой приложения. Решает объём (Т5, Т19) и нагрузка импорта на соседей.
2. **Как часто обновлять базу**, если дельты так и не появятся: раз в квартал полным
   импортом двух субъектов?
3. **Какая иерархия нужна порталу — административная или муниципальная.** От этого
   зависит, какие пути строить и что получит пользователь в строке адреса.

## 6. Порядок

1. **Т1–Т5** — безопасное подключение и объём. Без них гем нельзя положить в `Gemfile`
   приложения.
2. **Т6–Т9** — автодополнение в форме (первый экран справочника в админке).
3. **Т10–Т11** — перенос адресов из старой версии.
4. **Т12–Т14** — загрузка из приложения и эксплуатация.
5. **Т15–Т19** — по ходу.
