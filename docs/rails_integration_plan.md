## Контекст

Портал «Первоисточник» v4 (Rails 8.1, Ruby 3.4, PG 18, Puma с потоками, Solid Queue с форком,
ActiveAdmin + Tom Select) подключает гем для автодополнения адреса, переноса старых адресов,
определения региона и загрузки ГАР. Обновлять базу портал будет периодически, по крону из
фоновых задач. Требования — `docs/rails_integration_requirements.md` (Т1–Т19).

В 1.0.0 гем нельзя класть в Gemfile:
- по умолчанию он подключается к `DATABASE_URL` приложения;
- держит одно `PG::Connection` на процесс и не переживает `fork`;
- не имеет таймаутов;
- импортирует всю страну;
- в поиске нет границ, единой строки ввода и разбора адреса.

Порядок работы по просьбе пользователя: анализ → глубокий рефакторинг (с переработкой тестов) →
реализация требований → код-ревью и simplify. Работа идёт этапами в отдельных сессиях, прогресс
записывается в репозиторий, чтобы после любого этапа можно было остановиться и продолжить.

### Решения пользователя
- Публичный API **можно ломать** → **2.0.0**, CHANGELOG с разделом миграции.
- **Ruby >= 3.3**; результаты поиска — `Data`-классы.
- **Дельты обязательны** — один из последних этапов: от них зависит обновление по крону.
  Полный импорт остаётся для первой загрузки и как запасной путь.
- Состав загружаемых данных **настраивается** (наборы и тонкая настройка). По умолчанию —
  минимальный набор под задачи портала, так что достаточно указать базу и субъекты.
- Реальных данных сейчас нет: работаем на **синтетике**, но проектируем под большие объёмы
  (вся Россия тоже должна работать). Реальный прогон пользователь сделает у себя по скриптам и
  чек-листу.

### Технические решения (по умолчанию)
- Пул — гем `connection_pool`. Соединение обёрнуто в объект, который помнит `pid` владельца.
  В дочернем процессе унаследованные соединения **отбрасываются без `PQfinish`** (сокет
  переоткрывается в `/dev/null`, как `discard!` в Active Record). Иначе ребёнок пошлёт серверу
  Terminate и убьёт соединение родителя.
- Зависимости: убрать `mini_sql` (результаты станут `Data`, запросы — `exec_params`) и
  `httparty` (нужен только для двух GET); добавить `connection_pool`.
- Иерархия: обе, параметр `hierarchy:` у всех методов. По умолчанию
  `config.default_hierarchy = :adm` (вопрос портала §5.3 открыт).
- Код субъекта — двузначная строка, как имя папки в архиве (`"01"`, `"43"`). Импорт берёт
  его из папки, а не из `REGIONCODE`.

## Анализ 1.0.0

### Структура архива ГАР (проверено на `gar_xml_v20260116.zip`)
Оглавление получено скриптом `gar_toc.py` у пользователя. В этапе 0 полный вывод сохраняется
в `docs/gar_archive_structure.md`.

```
gar_xml_v20260116.zip   ZIP64, 1739 файлов, 49,25 ГБ сжато / 371,17 ГБ несжато
├── version.txt                         "2026.01.16\nv.223"
├── 10 справочников в корне             AS_ADDHOUSE_TYPES, AS_ADDR_OBJ_TYPES, AS_APARTMENT_TYPES,
│   (от 0,5 до 90 КБ)                   AS_HOUSE_TYPES, AS_NORMATIVE_DOCS_KINDS/_TYPES,
│                                       AS_OBJECT_LEVELS, AS_OPERATION_TYPES, AS_PARAM_TYPES,
│                                       AS_ROOM_TYPES
└── 96 папок субъектов: 01–95 и 99, вложенных папок нет
    └── ровно 18 файлов в каждой, по одному на таблицу:
        AS_ADDR_OBJ, AS_ADDR_OBJ_DIVISION, AS_ADDR_OBJ_PARAMS, AS_ADM_HIERARCHY, AS_MUN_HIERARCHY,
        AS_HOUSES, AS_HOUSES_PARAMS, AS_REESTR_OBJECTS, AS_CHANGE_HISTORY, AS_NORMATIVE_DOCS,
        AS_STEADS(_PARAMS), AS_APARTMENTS(_PARAMS), AS_ROOMS(_PARAMS), AS_CARPLACES(_PARAMS)
```

**Подробности**
- Имена файлов: `<ТАБЛИЦА>_<YYYYMMDD>_<guid>.XML`. Дата в имени (`20260115`/`20260116`)
  **не равна** версии выгрузки, версия берётся из `version.txt`.
- Папки 80, 81, 82, 84, 85 и 88 (бывшие субъекты) содержат все 18 файлов, но почти пустые.
- Несжатые объёмы по всей стране, всего по таблице / самый большой файл:

  | Таблица | Всего | Самый большой |
  |---|---|---|
  | `AS_HOUSES_PARAMS` | 89,6 ГБ | 4,8 |
  | `AS_CHANGE_HISTORY` | 61,2 ГБ | — |
  | `AS_STEADS_PARAMS` | 49,9 ГБ | — |
  | `AS_ADM_HIERARCHY` | 36,6 ГБ | 4,0 |
  | `AS_MUN_HIERARCHY` | 35,7 ГБ | — |
  | `AS_HOUSES` | 20,9 ГБ | 1,3 |
  | `AS_REESTR_OBJECTS` | 20,6 ГБ | — |
  | `AS_ADDR_OBJ_PARAMS` | 4,4 ГБ | — |
  | `AS_ADDR_OBJ` | 0,6 ГБ | — |

- Субъект 43: 3,73 ГБ несжато; субъект 11: 2,10 ГБ.
- Нужные порталу файлы двух субъектов (`ADDR_OBJ`, `ADDR_OBJ_PARAMS`, обе иерархии,
  `HOUSES`, `HOUSES_PARAMS`) — **2,95 ГБ XML (≈ 307 МБ сжато), 0,8 % архива**. Самый крупный
  из них — `43/AS_HOUSES_PARAMS`, 938 МБ.
- Типы параметров (`AS_PARAM_TYPES`): 5 — почтовый индекс, 6 — ОКАТО, 7 — ОКТМО,
  10 — код КЛАДР, 12 — код региона, 16 — официальное наименование.
  Действующий параметр: `CHANGEIDEND="0"`, `ENDDATE="2079-06-06"`.
- В XML пустые атрибуты опускаются (у домов без корпуса нет `ADDNUM1`, у иерархии часто нет
  `AREACODE`…). В `AS_ADDR_OBJ` лежат и исторические записи: у одного `OBJECTID` разный
  `LEVEL` в разных записях.
- `REGIONCODE` в иерархии для 43 — `"43"`.

**Выводы для гема**
- Субъект = папка `NN/`. Выбор субъектов — это записи zip с префиксом `43/`, `11/` и записи
  корня. Ни распаковки, ни разбора чужих папок.
- В субъекте один файл на таблицу. Работ на таблицу: ~96 на всю страну, 2 на два субъекта,
  1 у справочника.
- Размеры различаются на порядки (4,8 ГБ против килобайтов), несжатый размер известен из
  оглавления. Отсюда:
  - одна очередь «таблица × субъект» на все таблицы, крупные файлы первыми;
  - прогресс по байтам (Т12).
- Код субъекта импорт берёт из имени папки и пишет в `region_code` при COPY.
- Версия — из `version.txt` внутри архива, а не из имени zip.
- Пустые файлы и папки — обычный случай, не ошибка.
- Параметры: `params` в 1.0.0 делится на две таблицы по источникам, `addr_obj_params` и
  `house_params`. Уникальность `ID` гарантирована внутри каждого файла ФНС, это и ключ upsert
  для дельт. Фильтр по умолчанию: `type_ids: [5, 6, 7, 16]`, только действующие.
- Для всей страны параметры домов — самая тяжёлая таблица (89,6 ГБ). Поэтому
  `house_params` отключаема, а фильтр по типам применяется при разборе.
- Иерархии содержат строки всех объектов, включая квартиры и участки. Нужно:
  - `config.hierarchies = %i[adm mun]` — можно оставить одну и вдвое сократить импорт;
  - после загрузки — опция «оставить строки только объектов из `address_objects`/`houses`»;
    выгоду оценить по чек-листу на реальных данных.
- Дельта-архив пока не смотрели. Перед этапом 9 запустить тот же `gar_toc.py` на
  `GarXMLDeltaURL`.
- `OBJECTGUID` в ГАР — бывший `AOGUID` ФИАС (по описаниям формата). Подтвердить на выборке
  субъекта 43 (Т10).

### Какие данные нужны и как выбирать, что загружать

Объёмы — XML без сжатия: вся страна / субъекты 43+11.

|---|---|---|---|

| `ADDR_OBJ` | 0,6 ГБ / 12 МБ | регионы, города, улицы; исторические записи = старые названия | minimal |

| `HOUSES_PARAMS` | 89,6 ГБ / 1,43 ГБ | индекс (5), ОКАТО (6), ОКТМО (7), кадастровый номер (8) | minimal, по типам |
| `ADDR_OBJ_DIVISION` | 1 МБ / 18 КБ | связи разделения и переподчинения объектов (родитель → дети), помогают переносу старых адресов | extended |

| `STEADS` (+`_PARAMS`) | 6,0 + 49,9 ГБ / 112 МБ + 1,04 ГБ | земельные участки — адреса без дома (промзоны, сельские) | extended |
| `APARTMENTS`, `ROOMS` (+`_PARAMS`) | 16 + 22,5 ГБ / 279 + 371 МБ | помещения, квартиры, офисы, комнаты | extended |
| `CARPLACES` (+`_PARAMS`) | 0,4 ГБ / 1 МБ | машино-места | full |
| `CHANGE_HISTORY` | 61,2 ГБ / 1,0 ГБ | журнал операций над объектами (аудит) | full |
| `NORMATIVE_DOCS` | 6,2 ГБ / 140 МБ | документы-основания присвоения названий | full |

**Наборы (`config.preset`)**
- `:minimal` — по умолчанию; ровно то, что нужно порталу и функциям гема (поиск,
  автодополнение, `Gar.address`, `match_house`):
  - только актуальные записи;
  - параметры типов `[5, 6, 7, 16, 22, 23]`;
  - на два субъекта — 2,95 ГБ XML.
- `:extended` — плюс участки, помещения и комнаты (параметры по тем же типам), реестр GUID,
  связи разделения, исторические названия улиц. На два субъекта ≈ 5,1 ГБ XML.
- `:full` — всё, включая историю записей, журнал изменений, документы и все типы параметров.

**Тонкая настройка поверх набора**
- `config.tables` — список таблиц, по умолчанию из набора; можно `+= %i[steads]`;
- `config.hierarchies = %i[adm mun]`;
- `config.param_types`;
- `config.keep_history` — хранить неактуальные записи;
- `config.region_codes`.

Минимальная настройка портала — `GAR_DATABASE_URL` в окружении и
`config.region_codes = %w[43 11]`; всё остальное по умолчанию.

**Как функции узнают, что загружено.** Список загруженных таблиц и параметров пишется в
`gar_meta`. Функции проверяют `gar_meta`, а не конфигурацию: база могла быть импортирована
с другими настройками.
- Без обязательной таблицы — понятная `Gar::ConfigurationError` (например, нет ни одной
  иерархии).
- Без необязательной — функция работает с меньшими данными (нет `house_params` →
  `postal_code: nil`).

**Улучшения поиска из уже загружаемых данных**
Без новых больших таблиц, войдут в этап 6:
1. **Синонимы** (`Gar::Synonyms`) — группы равнозначных слов, из трёх источников:
   - **справочники ГАР** (автоматически): `short_name` ↔ `name` из `address_object_types`,
     `house_types`, `add_house_types`, включая старые варианты сокращений (`г`/`г.`,
     `ул`/`ул.`). Читаются из базы и кэшируются на версию схемы.
   - **встроенный словарь гема** `lib/gar/data/synonyms.yml` — разговорные формы, которых
     нет в справочниках:
     - типы: `пр`, `просп`, `пр-т` → проспект; `б-р` → бульвар; `мкрн` → микрорайон;
       `пос`/`п` → посёлок; `дер` → деревня;
     - части дома: `к`, `корп` → корпус; `стр` → строение; `лит` → литера; `влд` → владение;
     - частые слова в названиях: `б`/`бол` → большая, `м`/`мал` → малая, `им` → имени,
       `ст` → старая.
   - **настройка приложения** `config.synonyms` — свои группы поверх встроенных, например
     `{ "проспект" => %w[пркт], "имени" => %w[им.] }`.
     `config.builtin_synonyms = false` отключает встроенный словарь.

   Как работает:
   - Индекс (при построении путей) содержит и короткое, и полное имя типа.
   - Запрос нормализуется в Ruby: регистр, `ё`, точки, дефисы. Каждое слово из группы
     синонимов разворачивается в OR всех её вариантов: `(пр | просп | проспект)`, у
     последнего слова — префикс.
   - Поэтому свои синонимы приложения работают **без переиндексации**.
   - Неоднозначность (`б` — «большая» или «бульвар», `д` — «дом» или «деревня») даёт оба
     варианта, порядок решает ранжирование.
   - Те же группы для частей дома использует разбор номеров (`HouseNumber`): «корп. 2»,
     «к2», «стр 1» (Т7, Т11).
2. `ё` → `е` при индексации и в запросе.
3. Ранжирование:
   - точное совпадение;
   - административный центр (параметры 22/23);
   - «вес» объекта — число домов в поддереве, считается при построении путей.
   Так «Киров» выдаёт г. Киров раньше деревень «Кировский», а улицы города идут раньше улиц
   посёлков.
4. Поиск по индексу: запрос из 6 цифр ищет объекты с этим почтовым индексом.

**Для наборов extended/full**
Отдельный необязательный этап 15 (в ранних записях — 12), если понадобится:
- участки и помещения в поиске и `Gar.address`;
- поиск по старым названиям (бывш. ул. …);
- определение любого GUID через реестр;
- связи разделения при переносе адресов.

### Архив и распаковка в 1.0.0
Распаковка частичная, но только **по таблицам**: отбора по субъекту в коде нет
(`lib/gar/importer.rb:349-361`; Т5 это и требует). Для каждой таблицы из `import_entities`
`extract_xml_for_table` открывает zip и извлекает записи, имя которых **содержит** `XML_KEY`.
Проблемы:
1. **Нет фильтра по субъекту**: для каждой таблицы извлекается её файл из каждой из 96 папок.
2. **Подстрока захватывает чужие файлы**, и они ещё и парсятся (0 записей, но полный
   SAX-проход):
   - `AS_ADDR_OBJ` ловит `AS_ADDR_OBJ_PARAMS` (4,4 ГБ), `AS_ADDR_OBJ_DIVISION` и корневой
     `AS_ADDR_OBJ_TYPES`;
   - `AS_HOUSES` ловит `AS_HOUSES_PARAMS` — **89,6 ГБ, самая большая таблица архива**;
   - `AS_PARAM` находит только корневой `AS_PARAM_TYPES` (элемент `PARAMTYPE` ≠ `PARAM`).
     Файлы `*_PARAMS` не подходят ни под один ключ, поэтому **`params` всегда пуста**: индекса,
     ОКАТО и ОКТМО в базе нет.
3. **Удаление только в самом конце** (`ensure` в `import_tables`, после всех таблиц и
   индексов). По реальному оглавлению полный импорт с настройками по умолчанию:
   - распаковывает **≈ 208 ГБ** XML (плюс 49 ГБ сам zip);
   - из них 94 ГБ — чужие `*_PARAMS`, парсятся впустую;
   - ещё 20,6 ГБ — `reestr_objects`, которую никто не использует;
   - README при этом обещает «150 ГБ свободного места».
4. `entry.extract(path) unless File.exist?(path)`: если прошлый запуск убит на середине,
   обрезанный файл молча берётся повторно — часть данных теряется или падает парсер.
5. Параллелизм только по файлам (субъектам) внутри одной таблицы, таблицы идут по очереди.
   На полной базе это хорошо (96 файлов), но каждая таблица ждёт свой самый большой файл
   (до 4,8 ГБ). На двух субъектах работают максимум 2 воркера.

**Что делаем:**
- Записи выбираются по папке субъекта (`region_codes` + корень) и по точному имени
  `<KEY>_\d{8}_` в пределах папки.
- Чтение потоком из zip (`get_input_stream` → Ox SAX) без распаковки на диск.
- Запасной вариант — распаковать один файл во временный и удалить сразу после импорта
  (пик — один файл на воркер).
- Выбор между ними — по замеру на синтетическом файле в этапе 1.
- Одна очередь работ «таблица × субъект» для всех таблиц, крупные первыми; таблицы между
  собой не зависят, PK и индексы строятся после загрузки.

### Импорт и схема данных
6. Версия берётся из имени zip (`_v(\d+)\.zip$`), хотя внутри архива есть `version.txt`.
   При чужом имени `extract_version_from_archive` возвращает `0` → схема `gar_v0`.
7. `import_full_base` в начале удаляет `gar_v<ver>`, даже если это текущая схема (пример 3
   настраивает `database_schema` на версионную схему).
8. `backup_current_schema` ловит любой `StandardError` и пишет «схема не существует»
   (`importer.rb:142`); `drop_schema` глотает ошибки (`importer.rb:92`).
9. `find_latest_full_base_zip` берёт самый свежий `.zip` по mtime. Загрузка идёт прямо в
   итоговый файл, поэтому крон может импортировать недокачанный архив. Нужно качать в `.part`
   и переименовывать в конце.
10. Горячий цикл на каждую запись: `Date.parse` → `strftime`, `Hash`, диспетчер
    `format_value_for_copy`, `name.to_s` на каждый атрибут. При этом `"" .to_i` даёт `0` вместо
    `NULL`. Даты в XML уже `YYYY-MM-DD`, значит строку COPY можно собрать сразу.
11. PK создаётся до COPY и поддерживается при загрузке. Быстрее добавить PK вместе с индексами
    после загрузки, плюс `synchronous_commit=off` и `maintenance_work_mem` на сессию импорта.
    После загрузки нет `ANALYZE`.
12. `reestr_objects` (вся страна, все уровни, включая квартиры) импортируется по умолчанию, но
    поиск и пути её не используют.
13. Нет индексов на `object_guid` в `address_objects` и `houses`: все поиски по GUID идут
    seq scan.
14. Производные колонки (`full_*_path`, `*_tsv`) добавляются через `ALTER TABLE` и
    отсутствуют в DDL.

### Пути (`FullPathBuilder`)
15. Четыре почти одинаковых SQL; на каждый батч лишний запрос `MAX(id)`;
    `regexp_split_to_array` там, где хватит `string_to_array`.
16. Условие по `ao.is_active` без `is_actual`: при импорте без фильтра в путях появятся дубли.
    Если `house_num` равен `NULL`, путь дома тоже `NULL`.
17. Пакетный UPDATE свежей таблицы удваивает её размер. Сейчас помогает `VACUUM` каждые
    50 батчей; на реальных объёмах оценить альтернативу.

### Поиск
18. Повторяются списки колонок; ветвление `path_type` непоследовательно (`== :adm` / `== :mun`).
    Поиск по имени — три запроса (имя, счётчик, путь); лишний `DISTINCT`; имя схемы без
    `quote_ident`.
19. README обещает `find_address_objects(level: [2, 5, 6])`, но SQL делает `ao.level = :level`.
    Описанных в README `populate_full_paths` и `get_hierarchy` не существует.

### Соединения, загрузчик, прочее
20. Одно соединение на процесс; мьютекс защищает только его создание. Воркеры `:processes`
    наследуют соединение родителя.
21. `Downloader` печатает прогресс через `print`, `version_info` тянет все версии, `httparty`
    используется ради двух GET.
22. Мёртвый и дублирующийся код:
    - `Gar::Xml::*`, `NullParser`, `split_into_chunks`, `create_indexes_parallel`;
    - `table_name/column_name/column_type`, `PARSER_CLASS` (дублирует `case` в `XmlParser`),
      `DEFAULT_PARSER_OPTIONS`;
    - `all_table_names` при наличии `importable_tables`;
    - два `full_table_name`; `NullLogger` и запутанный `resolved_logger?`;
    - 20 файлов `entities/*` с повторяющимися заголовками, разбором и фильтрами.

## Анализ тестов

**Инфраструктура**
- Любой спек, даже `format_bytes`, требует PostgreSQL: `before(:suite)` запускает
  docker-compose и ждёт до 30 с.
- Теги `:integration` и `:slow` ничего не фильтруют. Переменную `INTEGRATION_TESTS` из
  Rakefile никто не читает.
- `search_spec` зависит от фикстур, которые заливает **не сам набор тестов**, а init-скрипты
  Docker (`db-test.Dockerfile`) или шаг `psql` в CI.
- DDL продублирован трижды: сущности, `spec/fixtures/schema.sql` и свой вариант с другими
  колонками в `full_path_builder_spec`.
- Глобальная конфигурация меняется через `allow(Gar.configuration)` и присваивания без сброса.
  Фиксированные имена схем (`gar_backup_v20241101`) и путей в `/tmp` мешают параллельным
  прогонам.
- Покрытие не меряется; CI — PG 13 (EOL), только `main`.

**Качество**
- Около 70 % примеров — «белый ящик»:
  - вызовы приватных методов через `send`;
  - моки собственных методов: «`import_table` вызван дважды», «методы в правильном порядке»;
  - подстроки SQL: «содержит `WITH batch_ids`»;
  - в `download_file` замокан сам `perform_download`, ретраи HTTP не проверяются.
  Такие тесты ломаются от любого рефакторинга и не проверяют результат.
- Тесты закрепляют ошибки и мёртвый код: «`drop_schema` — silent fail», «backup не падает»,
  `split_into_chunks`, `create_indexes_parallel`. Четыре контекста `#create_indexes` проверяют
  одно и то же.
- Слабые проверки:
  - `search_spec` почти везде проверяет только `be_an(Array)`: в фикстурах нет домов и
    регионов, подходящих под запросы;
  - импорт проверяется как `count >= 1` по одной таблице, пагинация путей — как `>= 100`.
- Не покрыто вовсе:
  - выбор файлов в архиве (поэтому ошибка 2 и не всплыла);
  - фильтры парсеров на настоящем XML, пустые значения;
  - параллельный импорт целиком;
  - ранжирование поиска, разница adm/mun;
  - ошибки соединения в поиске, несколько регионов в архиве.
- Фикстуры — случайная выборка по стране без цельной иерархии.

**Целевая стратегия**
1. Слои:
   - **unit без БД** — `Schema`/DDL, SAX-ридер на строках XML, кодирование COPY,
     `HouseNumber`, сборка адресной строки, конфигурация. Работают без PostgreSQL.
   - **интеграционные `:db`** — БД поднимается лениво, только для них.
2. Каждый `:db`-пример работает в своей уникальной схеме (хелпер `isolated_schema`) и сам
   её убирает. Фикстуры грузятся через `Gar::TestSupport` — тот же код, что получит
   приложение.
3. **Сквозной тест конвейера** на синтетическом архиве. Builder-DSL в `spec/support`
   повторяет реальную структуру:
   - `version.txt`, 10 справочников в корне;
   - папки субъектов с полным набором из 18 файлов, включая «шумовые» `*_PARAMS`,
     `_DIVISION`, `CHANGE_HISTORY`;
   - дата в именах файлов отличается от версии;
   - пустой субъект; исторические записи; опущенные атрибуты.
   Цепочка: импорт → пути → поиск/адрес с **точными** ожидаемыми значениями. На том же DSL —
   тесты регионов и дельт.
4. Проверяется только публичное поведение. Моки — только на внешних границах (HTTP через
   WebMock, время, недоступный хост).
5. Табличные спеки: `HouseNumber`/`match_house` на примерах старых адресов; строка ФНС на
   **точном примере из правил** («Московская область, городской округ Павлово-Посадский,
   город Павловский Посад, улица Тихонова, дом 93» и «дом 7 корпус 6 строение 2»): эта
   цепочка объектов кладётся в фикстуры.
6. Отдельно — спеки потоков, fork и таймаутов.
7. `:slow` (средний синтетический объём) локально по умолчанию выключен, в CI включён.
   Бенчмарки — вне rspec.
8. SimpleCov с порогом. CI на PostgreSQL 16 и 18, Ruby 3.3/3.4/последняя, на всех push/PR.

## Прогресс между сессиями

- `docs/rails_integration_plan.md` — копия плана в репозитории: чек-листы этапов, «Решения»,
  «Журнал сессий» (дата, что сделано, отклонения, что дальше).
- `CLAUDE.md` — соглашения (комментарии и логи на русском, rubocop, тестовая БД в облаке)
  и указание: «начни с `docs/rails_integration_plan.md`, выполни первый незавершённый этап».
- Конец каждого этапа:
  1. `bundle exec rubocop` чист;
  2. `bundle exec rspec` зелёный;
  3. `/simplify` по диффу этапа;
  4. журнал обновлён;
  5. commit и `git push -u origin rails-integration`;
  6. PR `rails-integration` → `release-2` «Этап N: …»; сливает пользователь («Squash and merge»).
- Ветки: `release-2` — интеграционная ветка 2.0 (только PR этапов); `rails-integration` —
  рабочая, после слияния PR пересоздаётся от `origin/release-2`; `main` остаётся на 1.x до
  финального PR `release-2` → `main` с версией 2.0.0 и тегом `v2.0.0`.
- Новая сессия начинается фразой «Продолжи работу по docs/rails_integration_plan.md».
